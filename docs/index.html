ESP32-C5 · 802.11 Probe Request · SSD1306

PasserbyCount 实现原理

用一块 ESP32-C5 的 Wi-Fi 射频在混杂模式下监听周围的 Probe Request， 按 MAC 去重并做滑动窗口统计，估算身边有多少人，最后在 1.3 寸单色 OLED 上实时显示。

01目标与约束

要做的事情只有一句话：不开热点、不连路由器、不碰任何人，仅靠"听"来估计周围有多少台 Wi-Fi 设备。 手机在连接 Wi-Fi 之前会主动广播 Probe Request（探测请求），这类帧是明文的管理帧， 内容里有发送方的 MAC 地址和接收信号强度，因此可以被动统计。

设计时被约束住的几个点，直接决定了后面的所有取舍：

  • 不能阻塞 Wi-Fi 任务。抓包回调跑在驱动任务里，一旦耗时过长，后续帧会被丢弃，统计直接失真。
  • 不能动态分配内存。回调频率可达上千帧每秒，任何 malloc 都可能造成碎片和不可预测的延迟。
  • 单射频只能守一个信道。ESP32-C5 只有一套 Wi-Fi 射频，想覆盖多个信道只能跳频，跳频期间必然漏帧。
  • 屏幕是 1bpp。只有亮和不亮两种状态，没有灰度、没有抗锯齿，字体和图形都必须按"纯二值"来设计。

03系统架构

整个固件由 3 个自有任务 + Wi-Fi 驱动任务构成，数据单向流动，层与层之间只通过队列和快照交互。

Wi-Fi 射频（单射频，只守一个信道） │ │ 混杂模式回调：只做 3 个判断，然后入队，绝不阻塞 ▼ ┌─────────────┐ │ RX Queue │ 128 条 × 8 字节 ≈ 1KB，满了丢帧 └─────────────┘ │ ▼ sniff_rx 任务（优先级 5） ├──► people_counter_feed() FNV-1a 哈希 + 组相联查表，O(1) ├──► people_counter_tick() 每秒一次，重算窗口人数/历史曲线 └──► 每 10 秒串口打印一行统计 │ │ 快照拷贝（临界区，< 60 字节） ▼ ┌──────────────────────────────┐ │ pc_snapshot_t │ └──────────────────────────────┘ │ ▼ lvgl 任务（优先级 2）── ui.c 的 lv_timer 每 500ms 取快照 │ │ I1 位图 → 页纵向位序重排 ▼ OLED 显存 1024 字节 ──I2C 400kHz──► 屏 另有 wifi_hop 任务（优先级 4）：每 300ms 切一次信道
关键点：没有任何一层直接调用下一层。抓包层不知道统计层的存在，统计层不知道屏幕的存在， 唯一的耦合是 pc_snapshot_t 这个只读快照结构。这样任何一层出问题都不会拖垮另一层。

04抓包层：混杂模式怎么拿到 Probe Request

4.1 进入混杂模式

先用 WIFI_MODE_NULL 初始化 Wi-Fi——不建 netif、不连任何 AP，只是把射频和 MAC 硬件拉起来， 这样既不占 IP 资源，也不会出现在别人的网络里。然后打开混杂模式，让硬件把所有收到的帧都送到回调， 而不是只接收发给自己的帧。 

esp_wifi_init(&cfg);                 // cfg 里把 RX 缓冲调大
esp_wifi_set_storage(WIFI_STORAGE_RAM);
esp_wifi_set_mode(WIFI_MODE_NULL);
esp_wifi_set_country_code("CN", true);
esp_wifi_start();

wifi_promiscuous_filter_t filter = { .filter_mask = WIFI_PROMIS_FILTER_MASK_MGMT };
esp_wifi_set_promiscuous_filter(&filter);
esp_wifi_set_promiscuous_rx_cb(sniffer_rx_cb);
esp_wifi_set_promiscuous(true);

过滤器只放管理帧。注意故意不设置 WIFI_PROMIS_FILTER_MASK_FCSFAIL， 这样 CRC 校验失败的残帧根本不会上送，回调里就少了一层判断。

4.2 一帧里我们关心什么

802.11 管理帧的头部是固定 24 字节，结构如下：

偏移长度字段说明
02Frame Control高 4 位是子类型，bit2~3 是类型
22Duration忽略
46Addr1接收方（广播帧是 FF:FF:FF:FF:FF:FF）
106Addr2发射端 = 终端自己的 MAC，这才是我们要的
166Addr3BSSID，探测请求里通常也是广播
222Sequence忽略

只认三种子类型，它们的共同点是"终端主动发起、携带真实源 MAC"：

子类型名称为什么算
4Probe Request手机扫描周围 AP 时广播，最主要的信号源
0Association Request连上 AP 的瞬间发出，说明人确实在现场
2Reassociation Request漫游时发出，同上

回调里还要做一道信号强度筛选：低于 -85dBm 的帧直接丢弃。 这一刀把"马路对面/上一层楼"的设备切掉，让统计口径更接近"周边"而不是"能收到的一切"。

4.3 为什么回调里不能干重活

回调运行在 Wi-Fi 驱动任务（优先级 23）的上下文里。如果在这里解析 IE、查表、写屏幕， 轻则丢帧，重则触发看门狗复位。所以回调只做三件事： 

static void sniffer_rx_cb(void *buf, wifi_promiscuous_pkt_type_t type)
{
    // 1. 长度 / RSSI 两个快速筛选
    // 2. 判断类型与子类型
    // 3. 拷贝 7 字节（MAC + RSSI）入队，非阻塞
    if (xQueueSend(s_queue, &rec, 0) != pdTRUE) {
        s_dropped++;
    }
}

4.4 信道跳频

单射频同一时刻只能守一个信道，而 Probe Request 会出现在 1/6/11 三个互不重叠的主信道上 （这三个信道覆盖了绝大多数 AP 的部署）。wifi_hop 任务每 300ms 调一次 esp_wifi_set_channel()，轮一圈 0.9 秒。

跳频期间收不到帧，这是物理限制，无法消除。缩短驻留时间能提高覆盖频率，但每次切换本身也有开销， 实测 300ms 是比较均衡的取值。

C5 支持 5GHz，把 PC_HOP_5G 改成 1 会切换成 WIFI_BAND_MODE_AUTO 并加入 5G 信道。国家码设成 CN 时，合法 5G 信道是 36~64（含 DFS）和 149~165——这个范围就是开机日志 wifi_5g_channel_mask=0x3e001fe 里那几个 bit。

05统计层：MAC 去重与滑动窗口

5.1 为什么是"组相联表"而不是链表或哈希桶

需求很明确：O(1) 查询、零动态分配、冲突时优雅降级。 链表需要遍历、哈希桶需要 malloc、开放寻址在删除时会破坏探测链。 最终选了固定大小的组相联（set-associative）结构： 

FNV-1a(mac) ──► 组号 = hash & 127      → 128 个组
                                    └─ 每组 4 个槽位，组内线性比较
                         总共 512 个槽位 × 16 字节 = 8KB 静态内存

每个槽位 16 字节：

字段大小用途
mac[6]6B设备 MAC
random1B本地管理位，标记随机化 MAC
rssi1B最后一次的信号强度
hits2B命中次数；为 0 表示槽位空闲
last_ms4B最后一次出现的时间戳

5.2 查表流程

1. 组播位为 1            → 直接丢弃（不可能是终端）
2. 组内 4 个槽位比对 MAC  → 命中则更新 last_ms / rssi / hits，返回
3. 组内有空槽            → 占用，total++
4. 组满了                → 踢掉组内 last_ms 最小的那个，写入新 MAC，total++

哈希冲突的后果被限制在"同一组的 4 个 MAC 互相挤占"，不会算错已有 MAC， 最坏情况只是提前忘记某个设备（current 少 1，total 可能重复计 1）。 512 个槽位在商圈、餐厅、地铁口这类场景下足够。

5.3 滑动窗口

"当前人数"不是计数器，而是每秒重算一次的状态量： 

current = 满足 (now - last_ms) <= 60000ms 的槽位数量

这样人走开 60 秒后自动从统计里消失，不需要任何"减一"操作，也就不存在漏减导致的数值漂移。 每秒扫一遍 512 个槽位，在 240MHz 的 RISC-V 上是微秒级开销。

除了 current，同一趟扫描还顺便算出：

  • peak：开机以来 current 的最大值（只增不减）；
  • total：开机以来累计去重过的 MAC 数量；
  • rssi_avg：窗口内所有设备的平均信号强度，可以粗略反映"离得多近"；
  • rate：上一秒的帧速率，用来判断当前信道有多"忙"。

5.4 历史曲线

保留最近 42 秒的 current 值，用环形方式推进：每次 tick 时整体右移一格，新值写进 hist[0]。这 42 个字节就是屏幕上那 42 根柱子的数据源。

5.5 快照与并发

统计结果不是直接读全局变量。tick 把结果写进 s_pub， 界面侧用 people_counter_get() 在临界区里整块拷走（不到 60 字节）。 临界区短到不会影响抓包任务，同时保证界面永远看到一个自洽的数值组合，不会出现 "人数是新的、峰值是旧的"这种撕裂。

06显示层：从 LVGL 位图到 SH1106 显存

这一层是整份代码里最容易踩坑的地方，有两处硬件特性必须处理。

6.1 为什么不用 esp_lcd 自带的 SSD1306 驱动

1.3 寸 4 脚 I2C 模块绝大多数其实是 SH1106 而不是 SSD1306。 两者显存宽度不同：SH1106 是 132 列（128 像素居中，左右各空 2 列），SSD1306 是 128 列。 更关键的是 SH1106 不支持 SSD1306 的 0x20/0x21/0x22 寻址命令， 用 SSD1306 驱动会看到整屏雪花。

解决办法是只用两种芯片都支持的命令集——页寻址： 

0xB0 | page        设置页地址（0~7）
0x00 | (col & 0x0F) 列地址低 4 位
0x10 | (col >> 4)     列地址高 4 位
然后连续写 128 字节    页内列地址自动 +1

这也是 SSD1306 上电后的默认模式，所以同一套代码两种屏都能跑。 列偏移做成宏 OLED_COL_OFFSET：SH1106 填 2，SSD1306 填 0。

6.2 位序重排：LVGL 是横向的，屏是纵向的

两个内存布局正好差 90 度的转置关系：

LVGL（I1 格式）OLED 显存
排布方向行优先，逐行铺开按页纵向堆叠
字节内MSB 在左（bit7 是最左像素）LSB 在上（bit0 是最上面一行）
一字节表示同一行的 8 个像素同一列的 8 个像素

所以 LVGL 交出来的缓冲区不能直接推给屏，必须在 flush_cb 里逐像素做一次位搬运： 

for (int y = 0; y < 64; y++) {
    for (int x = 0; x < 128; x++) {
        bool on = px_map[(128 / 8) * y + (x / 8)] & (1 << (7 - x % 8));
        uint8_t *buf = &s_fb[(128 * (y / 8)) + x];
        if (on) *buf |=  (1 << (y % 8));
        else    *buf &= ~(1 << (y % 8));
    }
}

8192 次循环，在 240MHz 上约 0.1ms，相比 I2C 传输时间可以忽略。

6.3 刷新一次要多久

整屏 1024 字节，加上每页 3 条命令，400kHz 下大约 25ms。 LVGL 用 LV_DISPLAY_RENDER_MODE_FULL 渲染，每次都是整屏重画； 但 LVGL 只会对"发生变化的对象"触发重绘请求，界面没变化时根本不会调用 flush， 所以稳态下 I2C 占用很低。

07并发与时序

任务优先级栈职责
Wi-Fi 驱动任务23—收包、进回调
sniff_rx54KB出队、查表、每秒统计、日志
wifi_hop43KB每 300ms 切信道
lvgl26KB跑 lv_timer_handler()，500ms 刷新界面

两个需要特别说明的同步点：

  • 队列负责跨任务传数据。长度为 128，满了就丢帧并计数（drop）， 不做等待——宁可丢一帧，也不能让 Wi-Fi 任务卡住。
  • 临界区只保护快照拷贝。表本身只在 sniff_rx 一个任务里读写， 所以 feed() 和 tick() 之间完全不需要加锁。
一个容易忽略的细节：rx_task 每次取到一帧后会先把队列里剩下的全部吃完， 然后再检查"是否过了一秒"。这样可以避免高流量时因为循环一直走出队分支而漏掉 tick。

09精度与局限

这套方案统计的是"唯一 MAC 数"，不是"人数"。 下面每一条都会让这两者产生偏差，产品化时必须用现场数据标定。

会高估的因素

  • MAC 随机化。iOS / Android 在扫描时会用随机 MAC，同一台手机每轮换一个， 窗口越长重复计数越多。打开 PC_IGNORE_RANDOM_MAC 可以反向收紧，但会漏掉大部分现代手机。
  • 一人多设备。手机 + 手表 + 耳机 + 平板，各算一个。常见的折算系数在 1.5~2.5 之间。
  • 表满后的覆盖。被踢出表的 MAC 再次出现时会重复计入 total （current 不受影响）。

会低估的因素

  • 跳频空档。单射频轮一圈 0.9 秒，跳走的这段时间该信道上的帧全部丢失。
  • 设备不主动扫描。已连接 AP 且屏幕熄灭的手机很少发 Probe Request。
  • 信号门限。-85dBm 之外的设备不计入，等于给统计范围画了个圈。

时间维度上的滞后

Probe Request 不是连续发出的，因此人数变化天然滞后 10~60 秒。 这也是把窗口设成 60 秒的原因——窗口太短会让数字剧烈跳动。

没有时钟

板子上没有 RTC 电池，也不联网对时，所以"累计"是开机以来的累计， 不是"今日累计"。要做按天统计，需要加 SNTP 或外部 RTC，并在跨零点时清零。

串口自检

开机打印复位原因，运行中每 10 秒一行统计：

I (312) app: PasserbyCount boot, reset reason: POWERON
I (2450) oled: probe 0x3C -> ACK(在线)
I (2480) sniffer: promiscuous on, 3 channels, dwell 300ms, rssi_min -85dBm
I (12480) sniffer: now=12 peak=15 total=234 frames=1893 rate=18/s rssi=-67 ch=6 drop=0

drop 持续增长说明处理跟不上，优先调大 RX 缓冲或缩短 PC_HOP_DWELL_MS。
